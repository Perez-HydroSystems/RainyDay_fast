# Storm-catalog engine benchmarks — Talequah reference example

Test case: `Examples/Talequah/Talequah.json` — irregular domain (180×180 grid,
28×33 storm mask), 72 h duration, 10 storms, AORC Jul–Sep 2002 (92 daily files,
hourly). Machine: Apple M3 Max (16 cores). All runs verified with
`tools/compare_catalogs.py` against `tools/reference_catalog_fftperstep/`
(regenerated baseline, RainyDay_Env).

- **catalog scan timer** = the file-scanning part that the engines accelerate.
  This is the part that grows linearly with record length — the 20-year cost driver.
- **catalog timer** = scan + storm re-read/write (~0.05 min, engine-independent).

| Engine         | Env              | Scan (min) | Catalog total (min) | Scan speedup | Catalog identical? |
|----------------|------------------|-----------:|--------------------:|-------------:|--------------------|
| fft_perstep    | RainyDay_Env     |       0.30 |                0.35 |           1× | reference          |
| batchfft       | RainyDay_Env     |       0.12 |                0.17 |         2.5× | ALL PASS (bitwise) |
| batchfft_mp ×8 | RainyDay_Env     |       0.03 |                0.08 |          10× | ALL PASS (bitwise) |
| batchtf (Metal GPU + exact confirm) | RainyDay_Env_GPU | 0.30 |     0.35 |           1× | ALL PASS (bitwise) |
| batchfft       | RainyDay_Env_GPU |       0.12 |                0.17 | (same-env CPU ref) | ALL PASS (bitwise) |

Rough 20-year extrapolation (~80× more files, scan scales linearly):
fft_perstep ≈ 24 min → batchfft ≈ 10 min → batchfft_mp ≈ 2–3 min of scan time.
Remaining cost is NetCDF I/O; more workers / faster storage push it further down.

## batchtf: why it needs (and has) an exact-confirm step

Raw TF-Metal conv produced the same 10 storms, same x/y placements,
`basinrainfall` within ~8e-7 relative — but 3 storms had their 72-h windows
shifted by +1 to +2 h. Cause: adjacent hourly windows of the same storm are
often exact float ties (the marginal hours add zero rain); Metal's conv2d
rounds float32 differently than the CPU FFT (same precision, different
summation order — neither is "more accurate"), so ties break at a different
hour. No cross-backend arithmetic can reproduce the CPU FFT's bit patterns.

Fix (`catalog_select_confirmed` in RainyDay_functions.py): GPU values are used
only as a screen with error bound δ (`RAINYDAY_GPU_DELTA`, default 1e-3;
measured Metal error 7.8e-7). Any timestep whose value comes within δ of the
running catalog minimum — including every accepted timestep — is recomputed
with the exact CPU FFT (grouped into consecutive-file runs), and the selection
restarts until a pass needs no new recomputes. Catalog slots then only ever
hold CPU-exact values, so the result is bit-identical to 'batchfft' by
construction. On Talequah: converged in 2 passes, 82/92 files recomputed (the
short record keeps the catalog minimum low, so most timesteps screen as
"could matter"; on multi-decade records the recomputed fraction shrinks).
Net effect: GPU engine is exact but no faster than fft_perstep here — use
batchfft/batchfft_mp for production; batchtf is the validated GPU pathway.

## CONUS-domain benchmark (added later)

Same AORC data with the transposition domain set to the CONUS mainland
(`Examples/CONUS_Benchmark/`, Natural Earth boundary shapefile generated by
`tools/make_conus_shapefile.py`): 747×1734 subgrid (~1.3M cells, ~40× Talequah),
July 2002 (31 files, 744 timesteps), same Talequah watershed (28×33 mask).
Only 4 storms satisfy the 24-h separation in one month at CONUS scale (legacy
selection behavior, identical across engines). All engines verified ALL PASS
(bitwise) against the fft_perstep run; archives in `tools/conus_catalogs/`.

| Engine         | Scan (min) | Speedup | Catalog identical? |
|----------------|-----------:|--------:|--------------------|
| fft_perstep    |       2.16 |      1× | reference          |
| batchfft       |       0.37 |    5.8× | ALL PASS (bitwise) |
| batchfft_mp ×8 |       0.13 |   16.6× | ALL PASS (bitwise) |
| batchtf (Metal + exact confirm) | 0.80 | 2.7× | ALL PASS (bitwise) |

Takeaways: batching pays more as the domain grows (2.5×→5.8×) because compute,
not I/O, dominates; the GPU engine crosses from "no faster" (Talequah) to 2.7×
here, confirming the domain-size trend — about half of its 0.80 min is the
exact-confirm CPU recompute of all 31 files, a short-record artifact that
shrinks on long records. `batchfft_mp` remains the fastest CPU option.

Side finding: the storm-writing loop's `except OSError` silently swallowed
non-permission errors, so failed writes left storms missing from the catalog
with no message (triggered by passing a relative parameter-file path). The
non-13 branch now prints the error and re-raises. Always pass the config JSON
as an absolute path.

## Usage

Engine selection: `RAINYDAY_CATALOG_ENGINE=batchfft|batchfft_mp|fft_perstep|batchtf`
(default is `batchfft`; read at the top of `Source/RainyDay_Py3.py`; rectangular
domains always use the original catalogNumba path).
Tuning: `RAINYDAY_BLOCKFILES` (files per FFT batch, default 16),
`RAINYDAY_NWORKERS` (batchfft_mp workers, default = cores/2).

Run + verify:

```bash
bash RainyDay/tools/run_talequah.sh RainyDay_Env batchfft_mp
python RainyDay/tools/compare_catalogs.py RainyDay/tools/reference_catalog_fftperstep \
    RainyDay/Examples/Talequah/Results/Talequah_3days/StormCatalog
```

"Bitwise" = identical storm dates, x/y placements, cattime, and rain fields;
`basinrainfall` measured difference was exactly 0 in all passing runs
(tolerance allowed rtol 1e-5). Criterion details: header of `compare_catalogs.py`.
